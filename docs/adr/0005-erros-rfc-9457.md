# 0005. Erros no padrão RFC 9457 com `code` estável

- Status: **proposta — revisão do Alicerce**
- Data: 2026-11-13
- Decisores: Alicerce (dono), Quarteto Dev (texto)

## Contexto
Front, testes e quem integrar precisam decidir pelo tipo de erro, não pelo texto. A RFC 9457 substituiu a RFC 7807 e o Spring tem `ProblemDetail` nativo.

## Decisão
- Todo erro responde `application/problem+json`:

```json
{
  "type": "https://github.com/k3vinrich4rd/barbearia-altas-horas/blob/main/docs/contrato/contrato-api.md#horario_indisponivel",
  "title": "Horário indisponível",
  "status": 409,
  "detail": "Este horário acabou de ser reservado. Escolha outro.",
  "instance": "/agendamentos",
  "code": "HORARIO_INDISPONIVEL",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": []
}
```

- Extensões: `code` (estável, MAIÚSCULAS, catálogo único em `comum`), `traceId` (correlação com o log) e `errors[]` (`{ "field": "email", "message": "deve ser um e-mail válido" }`) só em validação.
- `type` aponta para a seção do erro no contrato (URI que abre no navegador).
- Código novo pode entrar; código existente **nunca** é renomeado (quebra o front).
- **Matriz de acesso:** `401` sem login ou token inválido; `403` logado sem o papel; `404` recurso de outro dono (não confirma que o id existe).
- Mensagens (`title`, `detail`, `errors[].message`) em português e **sem dado pessoal** (nada de "o e-mail fulano@... já existe").
- O catálogo completo está no [contrato, seção 5](../contrato/contrato-api.md#5-erros).

## Consequências
- ✅ Um formato para tudo, inclusive 401/403 da camada de segurança (o `AuthenticationEntryPoint` e o `AccessDeniedHandler` escrevem o mesmo JSON).
- ⚠️ Diferente do formato próprio de outros projetos do Kevin (`codigo`, `campos`): aqui vale o prompt aprovado (`code`, `errors`). Registrado em `decisoes.md`.

## Gatilhos para revisitar
- Cliente externo pedir outro formato → não muda; documentar.
